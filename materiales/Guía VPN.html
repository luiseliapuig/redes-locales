Concepto fundamental

¿Qué es una VPN?

Una VPN crea un túnel cifrado entre dos o más dispositivos a través de Internet, permitiendo que se comuniquen como si estuviesen en la misma red local privada.

El túnel Concepto

Imagina Internet como una carretera pública. Una VPN construye un tubo opaco dentro de esa carretera: el tráfico viaja por dentro y nadie desde fuera puede ver qué contiene ni de dónde viene realmente.

Virtual y privada Concepto

Virtual porque no existe físicamente — es software emulando una interfaz de red. Privada porque el tráfico va cifrado y solo las máquinas autorizadas participan en la red.

¿Qué hace exactamente? Técnico

  • Encapsula los paquetes originales dentro de nuevos paquetes cifrados (encapsulación).
  • Asigna a cada participante una IP dentro de la red virtual — por ejemplo 10.8.0.1, 10.8.0.2…
  • Todo el tráfico entre esas IPs viaja cifrado sobre la red real (Internet o LAN).
  • El receptor descifra el paquete y lo entrega al destino real de forma transparente para las apps.

Tipo 01 · Comercial

VPN Comercial

Servicios de VPN ofrecidos por empresas orientados a usuarios finales que buscan privacidad, seguridad en redes públicas o acceso a contenido geobloqueado.

🌐 Para usuarios finales · Sin configuración técnica
Cómo funciona

Funcionamiento básico

1

Instalas la app del proveedor

NordVPN, Surfshark, ExpressVPN… ofrecen apps para Windows, macOS, iOS, Android y Linux. Sin configuración manual de ningún tipo.

2

Eliges un servidor y te conectas

Puedes elegir el país o dejar que la app elija el servidor más rápido. Todo el tráfico de tu dispositivo se redirige a través de ese servidor.

3

Tu IP cambia y el tráfico va cifrado

Los sitios web ven la IP del servidor VPN, no la tuya. El tráfico entre tu dispositivo y el servidor viaja cifrado — tu ISP solo ve una conexión opaca hacia el servidor.

Casos de uso

¿Para qué se usa?

🔒 Seguridad en redes públicas

En cafeterías, aeropuertos u hoteles el Wi-Fi es compartido y potencialmente inseguro. Un atacante en la misma red podría interceptar tráfico no cifrado.

Con una VPN activa, todo el tráfico viaja cifrado desde tu dispositivo hasta el servidor VPN — aunque el Wi-Fi público sea hostil, nadie puede leer tus datos.

🌍 Contenido geobloqueado

Muchos servicios de streaming tienen catálogos diferentes por país. Al conectarte a un servidor VPN en EE.UU., tu IP aparece como estadounidense.

Importante: algunos servicios detectan y bloquean IPs de proveedores VPN conocidos. La eficacia varía según el proveedor y el momento.

🕵️ Privacidad frente al ISP

Tu proveedor de Internet puede ver qué dominios visitas (incluso con HTTPS, el DNS lo revela). Con una VPN, el ISP solo ve tráfico cifrado hacia el servidor.

⚠️ Limitaciones importantes

Confías en el proveedor: si guarda logs de tu actividad, tu privacidad depende de su honestidad y jurisdicción legal.

No te hace anónimo: si tienes sesión en Google o Facebook, te siguen identificando independientemente de la VPN.

Tipo 02 · Acceso remoto

VPN de acceso remoto

Un cliente individual se conecta a una red privada remota. Es lo que configuraremos: un servidor Ubuntu ejecutando WireGuard al que nos conectamos desde un cliente Ubuntu.

🔧 WireGuard · Ubuntu Server + Ubuntu Desktop
Requisitos

Infraestructura necesaria

🖥 Servidor VPN

  • Recibe y gestiona las conexiones entrantes.
  • Actúa como punto central y enruta el tráfico cifrado.
  • Necesita una IP o hostname accesible desde el exterior.
  • Puede ser un físico, VM, VPS en la nube o router compatible.
  • En nuestro caso: Ubuntu Server 22.04+

💻 Cliente VPN

  • Inicia la conexión hacia el servidor.
  • Una vez conectado, accede a los recursos de la red privada.
  • WireGuard tiene apps para todas las plataformas.
  • La interfaz virtual wg0 actúa como una tarjeta de red normal.
  • En nuestro caso: Ubuntu Desktop o cualquier Linux.
Conectividad

Red entre las máquinas

El cliente necesita poder llegar al servidor para establecer el túnel. Hay cuatro escenarios posibles.

A

Servidor con IP pública fija

El caso más sencillo. Habitual en VPS (Hetzner, DigitalOcean, AWS…). El cliente apunta directamente a esa IP en la configuración.

B

Servidor con IP dinámica + DDNS

Si la IP pública cambia (ISP doméstico), se usa un servicio DDNS (DuckDNS, No-IP…) que mantiene un hostname apuntando siempre a la IP actual. El cliente usa el hostname como endpoint.

C

Servidor detrás de NAT → Port Forwarding

Si el servidor está en una red doméstica, hay que configurar port forwarding en el router: redirigir el puerto UDP 51820 a la IP privada del servidor Ubuntu.

D

Ambos en la misma LAN (laboratorio)

Se usa directamente la IP privada del servidor (192.168.x.x) como endpoint. Ideal para prácticas sin necesidad de IP pública.

⚠

Firewall del servidor: abre el puerto UDP 51820 tanto en el SO (sudo ufw allow 51820/udp) como en cualquier firewall externo (panel del VPS, router…).

Criptografía

Cómo cifra WireGuard

Curve25519 Clave pública

Curva elíptica de alto rendimiento para el intercambio de claves Diffie-Hellman. Genera el secreto compartido a partir del par de claves de cada extremo.

ChaCha20-Poly1305 Cifrado

Cifra el contenido del túnel. ChaCha20 da confidencialidad; Poly1305 garantiza integridad. Más rápido que AES en hardware sin aceleración dedicada.

BLAKE2s Hash

Función de hash para derivación de claves y autenticación de mensajes. Más rápida que SHA-256 con seguridad equivalente.

Modelo de seguridad Ventajas clave

  • El handshake se repite cada 3 minutos: forward secrecy garantizado — robar una clave de sesión no descifra tráfico pasado.
  • Silence by default: WireGuard no responde a paquetes de claves no configuradas. Invisible ante escaneos de red.
  • IP roaming: si el cliente cambia de red (4G → Wi-Fi), la sesión sobrevive sin reconectar.
  • Sin negociación de algoritmos: no hay cipher suite que atacar.
Criptografía asimétrica

Par de claves pública / privada

Cada máquina genera su propio par. La privada nunca sale del dispositivo; la pública se intercambia manualmente con los peers.

En el servidor

bash
# Instalar WireGuard
sudo apt update && sudo apt install wireguard -y

# Generar claves
wg genkey | tee /etc/wireguard/server_private.key \
  | wg pubkey > /etc/wireguard/server_public.key
chmod 600 /etc/wireguard/server_private.key

# Ver claves generadas
cat /etc/wireguard/server_private.key
cat /etc/wireguard/server_public.key

En el cliente

bash
# Instalar WireGuard
sudo apt update && sudo apt install wireguard -y

# Generar claves
wg genkey | tee /etc/wireguard/client_private.key \
  | wg pubkey > /etc/wireguard/client_public.key
chmod 600 /etc/wireguard/client_private.key

# Ver claves generadas
cat /etc/wireguard/client_private.key
cat /etc/wireguard/client_public.key
⛔

La clave privada nunca se comparte ni se envía por la red. Solo compartes la clave pública. Si alguien obtiene tu clave privada, puede suplantar tu identidad en la VPN.

Configuración del servidor

wg0.conf — Servidor

ini/etc/wireguard/wg0.conf — Servidor
[Interface]
Address     = 10.8.0.1/24               # IP del servidor en la VPN
ListenPort  = 51820                    # Puerto UDP donde escucha
PrivateKey  = <CLAVE_PRIVADA_SERVIDOR>   # cat /etc/wireguard/server_private.key

# NAT: permite que el cliente salga a Internet por el servidor
PostUp      = iptables -A FORWARD -i wg0 -j ACCEPT; \
               iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PostDown    = iptables -D FORWARD -i wg0 -j ACCEPT; \
               iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE

# ── Cliente autorizado ───────────────────────────────
[Peer]
PublicKey   = <CLAVE_PUBLICA_CLIENTE>    # cat /etc/wireguard/client_public.key
AllowedIPs  = 10.8.0.2/32               # IP asignada a este cliente

Address Campo

IP del servidor dentro de la red virtual. El /24 reserva la subred 10.8.0.0/24 para la VPN. Elige un rango que no colisione con tu LAN real.

PostUp / PostDown Campo

Activar NAT para que el tráfico del cliente salga a Internet por la interfaz real del servidor. Reemplaza eth0 por tu interfaz: compruébala con ip route | grep default.

AllowedIPs peer Campo

IPs aceptadas de este peer. En el servidor se usa /32 porque cada cliente tiene una IP fija asignada. Para más clientes, repite el bloque [Peer].

Configuración del cliente

wg0.conf — Cliente

ini/etc/wireguard/wg0.conf — Cliente
[Interface]
Address             = 10.8.0.2/24               # IP del cliente en la VPN
PrivateKey          = <CLAVE_PRIVADA_CLIENTE>    # cat /etc/wireguard/client_private.key
DNS                 = 1.1.1.1                   # DNS activo con la VPN conectada

[Peer]  # El servidor
PublicKey           = <CLAVE_PUBLICA_SERVIDOR>   # cat /etc/wireguard/server_public.key
Endpoint            = <IP_O_HOSTNAME>:51820
AllowedIPs          = 10.8.0.0/24               # Split tunnel: solo tráfico VPN
PersistentKeepalive = 25                        # Mantiene el túnel activo tras NAT

AllowedIPs — Split vs Full tunnel

Split 10.8.0.0/24: solo el tráfico hacia la red VPN va cifrado. El resto sale directo. Mejor rendimiento.

Full 0.0.0.0/0, ::/0: todo el tráfico pasa por el servidor. Máxima privacidad.

PersistentKeepalive

Envía un paquete al servidor cada 25 segundos. Necesario cuando el cliente está detrás de NAT: mantiene la entrada en la tabla NAT del router para que el servidor pueda responder.

Tipo 03 · Sitio a sitio

VPN de sitio a sitio

Conecta permanentemente dos redes privadas a través de Internet. Los usuarios de cada sede acceden a recursos de la otra de forma transparente, sin configurar nada en sus dispositivos.

🏙 Para infraestructura corporativa · Conexión permanente
Concepto

Red ↔ Red, no dispositivo ↔ red

La diferencia clave Importante

En la VPN de acceso remoto, cada usuario configura WireGuard en su dispositivo. En la VPN sitio a sitio, la configuración está en los routers o firewalls de borde de cada sede. Los usuarios finales no saben que existe una VPN: simplemente acceden a recursos de la otra sede como si estuviesen en la misma red local.

1

Cada sede tiene un router/firewall con WireGuard

El router de la Sede A y el de la Sede B tienen WireGuard instalado y configurado. Cada uno actúa como peer del otro.

2

Se establece un túnel permanente entre los routers

El túnel se levanta al arrancar los routers y se mantiene activo indefinidamente. Si cae, se reestablece automáticamente en el siguiente keepalive.

3

El routing propaga las subredes de cada sede

Cada router anuncia su subred local a través del túnel. Un PC en Sede A (192.168.1.x) puede alcanzar servidores de Sede B (192.168.2.x) de forma transparente.

4

El usuario final no nota nada

Accede al servidor de la otra sede por su IP privada. El SO enruta el paquete al router local, que lo manda por el túnel cifrado sin que el usuario lo sepa.

Implementación

Configuración con WireGuard

WireGuard es simétrico: no hay "servidor" y "cliente" formales. Ambos extremos son peers. El que tiene Endpoint configurado inicia la conexión.

Router Sede A — LAN: 192.168.1.0/24

ini/etc/wireguard/wg0.conf
[Interface]
Address    = 10.10.0.1/30         # IP en el túnel VPN
ListenPort = 51820
PrivateKey = <PRIVKEY_SEDE_A>

PostUp     = iptables -A FORWARD -i wg0 -j ACCEPT; \
              iptables -A FORWARD -o wg0 -j ACCEPT
PostDown   = iptables -D FORWARD -i wg0 -j ACCEPT; \
              iptables -D FORWARD -o wg0 -j ACCEPT

[Peer]  # Router Sede B
PublicKey  = <PUBKEY_SEDE_B>
AllowedIPs = 10.10.0.2/32, 192.168.2.0/24
Endpoint   = <IP_PUBLICA_SEDE_B>:51820
PersistentKeepalive = 25

Router Sede B — LAN: 192.168.2.0/24

ini/etc/wireguard/wg0.conf
[Interface]
Address    = 10.10.0.2/30         # IP en el túnel VPN
ListenPort = 51820
PrivateKey = <PRIVKEY_SEDE_B>

PostUp     = iptables -A FORWARD -i wg0 -j ACCEPT; \
              iptables -A FORWARD -o wg0 -j ACCEPT
PostDown   = iptables -D FORWARD -i wg0 -j ACCEPT; \
              iptables -D FORWARD -o wg0 -j ACCEPT

[Peer]  # Router Sede A
PublicKey  = <PUBKEY_SEDE_A>
AllowedIPs = 10.10.0.1/32, 192.168.1.0/24
Endpoint   = <IP_PUBLICA_SEDE_A>:51820
PersistentKeepalive = 25
ℹ

Clave: el AllowedIPs de cada peer incluye la IP del túnel del otro router (/32) y la subred LAN detrás de él (192.168.x.0/24). Así WireGuard sabe que los paquetes hacia esa LAN deben ir cifrados por ese peer.

Routing

Que los PCs usen el túnel

Opción A — Ruta estática Manual

Añadir una ruta en cada PC: "paquetes a 192.168.2.0/24, ve por el router local 192.168.1.1".

bash
# En cada PC de Sede A
sudo ip route add 192.168.2.0/24 \
  via 192.168.1.1

Opción B — Default gateway Recomendado

Si el router ya es el default gateway de la LAN (lo normal en una red doméstica o empresarial), los PCs envían todo el tráfico desconocido al router sin ninguna configuración extra.

Solo hay que asegurarse de que el router tenga IP forwarding activo y las rutas correctas, que WireGuard gestiona automáticamente con AllowedIPs.

Activar IP forwarding en los routers Obligatorio

bashEn ambos routers
# Activar permanentemente
echo "net.ipv4.ip_forward = 1" | sudo tee -a /etc/sysctl.conf
sudo sysctl -p

# Verificar (debe devolver 1)
cat /proc/sys/net/ipv4/ip_forward

# Probar conectividad entre sedes
ping -c 4 192.168.2.1   # Desde Sede A al router de Sede B
ping -c 4 192.168.2.50  # Desde Sede A a un PC de Sede B
